# Recognition security audit, 2026-11-04

Scope: a security-focused review of the whole repository at the 2026-11-01 working state (everything through the cookie-import work, proposal 0009), with emphasis on the attack surface added since the last threat-model pass (`docs/proposals/THREAT_MODEL_V1.md`): the SQLite reader, the cookie importer, the kept library, zip handling, process spawning, and the internal-page message channel. Method: code review plus fuzzing of the new binary parser.

Adversaries considered (from the threat model): X1 malicious website / iframe, X4 malware running as the same user, X7 a crafted file the user (or malware) puts where the browser will read it, X5 supply chain.

## Result

Two real findings, both fixed in this change set; everything else reviewed was already protected. The security-relevant gates are green: the governed-actions self-test (the message gate), extension governance, locked startup, site policy, certificate manager, and the receipt self-tests. `browser.tests` 1170/1170; stress run green; publish scan clean; packet law green. (The 7 prove-all components that fail in the cloud need Windows DPAPI or `ssh-keygen` and pass on Windows CI — the same set prior audits recorded.)

## Findings fixed

| # | Severity | Finding | Fix | Guard |
|---|---|---|---|---|
| V1 | Medium (robustness / DoS hardening) | **The new read-only SQLite reader (`SqliteReader.cs`) threw raw `IndexOutOfRangeException` / `ArgumentException` on crafted or corrupt databases.** It reads another browser's cookie store (X7: malware under the same account could replace that file with a crafted one). Managed code, so no memory corruption, and the error was already caught per-source, but by this project's rule every parser must refuse hostile input with its own typed exception, not a raw crash. Fuzzing (40,000 malformed inputs) produced 18 raw exceptions. | The reader's whole parse is wrapped so any `IndexOutOfRange`/`Argument`/`Overflow`/`Format` from reading past a cell becomes a governed `SqliteException`. The reader still never writes and never runs anything; the worst a crafted file can do is be refused. | Re-fuzzed: 40,000 inputs, 0 raw exceptions, 0 hangs. Regression test: 400 crafted/corrupt databases all raise `SqliteException` |
| V2 | Medium (privacy, fail-open) | **F9 from the 2026-10-21 audit, deferred twice as the owner's call, now fixed.** `FilterEngine.Match` returned "not blocked" for any request URL longer than 4,096 characters, so a tracker on a blocked domain slipped through by padding its URL past that length. | The length cap no longer fails open: the padding sits in the path/query, after the host, so the engine matches the full host against a bounded prefix. Host rules (`||domain^`, hosts lists) block the request; matching cost stays bounded (same as a 4,096-char URL). | Executed test: a blocked host with an over-length padded URL is blocked, an unlisted host is not; stress test: a ~14,000-char padded URL on a blocked host is blocked; the pathological-rules timing guard still holds |

## Reviewed and already protected (no change needed)

- **The message channel (threat model F1).** Every page, including hostile sites and cross-origin iframes, can call `window.chrome.webview.postMessage`. `MessageGate.Classify` still accepts commands only from an internal page with a non-web source; web content gets only rate-limited allowlisted shortcuts. The new cookie-import commands (`ov-cookie-import*`) are handled inside the gated path and double-guarded by `tab.Internal == "overview"`, so a website cannot trigger reading or importing cookies.
- **Stored XSS into internal pages.** Internal pages run with `script-src 'unsafe-inline'`, so injected script would be privileged. All untrusted strings (page titles, URLs, download names, extension names, cookie site names) are either HTML-escaped (`Esc`), attribute-escaped with quote neutralization (`Attr`), or set as `textContent` / posted as JSON — no `innerHTML` sinks. Bookmark and history URLs are validated to http(s) only, so no `javascript:` links.
- **The cookie importer.** Reads only the user's own browsers under their Windows account; Chromium values are unwrapped with that account's DPAPI, so another user cannot. It only reads the other browser (share-mode, never writes to it), asks before importing, imports only into the normal profile (never a private tab), writes a receipt with no cookie names or values, and drops trackers by default. Expired, malformed, control-character and over-long cookies are refused before reaching the engine.
- **Zip handling.** Extensions and the kept library route every untrusted archive through the governed hostile-package unpacker (path-traversal, absolute/backslash/trailing-dot names, entry/size/ratio limits, symlink refusal). A kept extension's compressed copy is re-hashed through that same unpacker before its folder is removed, so a tampered archive is refused.
- **Process spawning.** The NFL receipt CLI and SoteriaVault are launched with an argument list (no shell string), `UseShellExecute=false`. The PowerShell string-argument launchers (export, update, self-update) take only install-internal paths, not web- or web-content-reachable input. Downloaded files open only for types that cannot run code; executables are gated at download time.
- **Extension governance and locked startup.** Identity = hash of the file list; the load gate recomputes it from bytes on disk and loads only if the latest ledger record says allow; unapproved extensions are removed from the engine profile at startup; broad-access permissions are denied, sensitive ones need explicit approval. Adding a removed extension back re-hashes it, re-runs the policy, and re-records the ledger — no short cut.

## Residual risk / out of scope (unchanged from the threat model)

- Rendering, JavaScript, networking, the process sandbox and most exploit mitigations are Chromium's (WebView2), patched on Microsoft's schedule, not Recognition's.
- Malware already running as the user can call DPAPI as that user (X4); encrypted-at-rest data defends against another user (X3), not against code running as you.
- The long-URL filter cost is bounded but a URL over the cap still has its path/query beyond the cap unmatched by path rules; host rules (the ones that block trackers) now always apply.
